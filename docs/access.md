# Google本人確認とグループ利用許可

スタッフの利用許可は、TourDBを編集共有している **ssj-sl-data-manager@googlegroups.com** の所属で判定します。スタッフの個人メールを利用許可リストへ登録しません。Googleで本人を確認できただけでは利用を許可しません。既存のDB所有者には、初回設定・写真保存先設定などの管理権限を維持します。

2026-11-27：Google上でGroupsAppの追加承認が不足していたことを確認し、保存済みMain.gsへ承認要求を追加しました。所有者から追加承認とGoogle本人確認完了の報告を受けています。今回の7日間保持・保持チェック・タブ終了はローカル実装で、Googleへ反映・デプロイしていません。実スタッフの読み書き・非メンバー拒否の本番確認は未完了です。

## スタッフの操作

1. 通常のWebアプリURL（末尾が /exec）を開きます。
2. 本人確認画面の「このブラウザーで本人確認を7日間保持する」を選びます。初回はONです。OFFなら、このタブ内だけ保持します（最大6時間）。変更した選択は次回にも残します。
3. 「Googleでログイン」を押し、指定グループに所属するGoogleアカウントを選びます。Googleのタブが開かなければ「Googleの確認画面を開く」を使います。
4. 確認用タブの自動終了を試み、元のタブでアプリを続けます。閉じない場合は「このタブを閉じて戻る」を押します。それでも閉じない場合は確認用タブを手動で閉じて元のタブを選びます。「アプリを開く」は元のタブを閉じていた場合に使います。
5. 本人確認中は元のアプリのタブを閉じず、そこで候補画面が表示されるまで待ちます。その後、保持ONなら同じブラウザープロファイルで通常のアプリURLを開き直せます。保持設定は、閉じるときに未保存の編集を自動保存する機能ではありません。

要求する本人確認情報は openid email のみで、スタッフ自身のSheets・Driveへのアクセス権は要求しません。Googleが既にアクセス者のアドレスをアプリへ提供している場合は、その情報で同じグループ判定を行います。保持ONでは同じブラウザープロファイル・同じアプリを開き直しても、ログインから最大7日間、Googleでの再確認を省けます。利用のたびに期限を延ばしません。ログアウト、接続設定変更、期限切れ、ブラウザー保存の削除で再確認が必要です。シークレットモードや保存制限がある環境では保持できない場合があります。保存が拒否された場合はタブ内だけの保持であることを画面に表示します。グループ所属とTourDBへの指定グループ共有は操作ごとに再照会し、脱退・共有取消は次の操作から拒否します。再確認では入力・選択を残すポップアップを開き、失敗した保存を勝手に再実行しません。別アカウントの本人確認を、編集中の操作へ黙って引き継ぐこともありません。

## 所有者が指定する取扱説明書URL

今回の更新後は「設定 → 取扱説明書 → 開く」でHTTPSのURLを一度設定します。取説URLは1つで、日本語・Englishは取説ページ内で切り替えます。旧2項目の設定は読み込み時に既存URLを継承し、所有者の保存時に単一URLへ移行して変更前後を記録します。アプリのヘッダー、本人確認画面、Googleログイン設定の取説リンクは同じ保存設定を使います。固定URLへのフォールバックはありません。リンク先は本人確認前にも表示されるため、認証情報を含むURLは登録しないでください。

変更APIは本人確認・DB所有者の判定・保存直前の再確認・設定版の競合検査を行います。スタッフが画面の所有者フラグを変えても設定APIは許可しません。ただし、実行用Apps Scriptそのものの編集権限を持つ人を、アプリ内の所有者判定だけで制限できるという意味ではありません。

## 所有者によるコード更新と初回登録

### 1. コードと既存デプロイを更新（登録済みなら再登録不要）

対象は[TourDB](https://docs.google.com/spreadsheets/d/1UGHv-DeBq2LEuLolF7hGVXXkZTBBlo1hE25Gy2_3s-M/edit)に紐づくApps Scriptです。

1. TourDBで「拡張機能 → Apps Script」を開き、既存のMain.gsとIndex.htmlを今回の全文で置き換えて保存します。同じ処理のファイルを重複追加しません。追加ファイルはありません。既存のDiscoveryWorker.htmlはそのまま使います。
2. 既存Webアプリのデプロイを新しい版へ更新します。実行者は「所有者」、アクセス範囲は指定済みの「Googleアカウントを持つ全員」です。新しいデプロイURLを作る必要はありません。
3. 所有者としてその /exec を開き、「設定 → Googleログイン → 設定を開く」を押します。表示された「Googleに登録する戻り先URL」をコピーします。

ローカルマニフェストのwebappはUSER_DEPLOYING / ANYONEへ揃えました。今回の追加スコープはありません。**Google側の既存appsscript.json全体を上書きしません。** 記念写真用など、既存oauthScopesを保持します。DBの初期化・列追加も不要です。

「接続情報：登録済み」と表示され、現在のログインが使えている場合は、以下の初回登録・JSON保存を繰り返しません。保持機能の更新だけで、OAuthクライアントの再作成、プロジェクト名・アプリ名の変更、接続設定版の更新は不要です。

| 確認するもの | ある場所と操作 |
| --- | --- |
| Main.gs・HTML Index | 対象TourDBの「拡張機能 → Apps Script」にある既存ファイルを置換して保存 |
| 既存マニフェスト | Apps Scriptの「プロジェクトの設定」でマニフェストの表示を有効にすると、ファイル一覧へappsscript.jsonが出る。必要な要素だけ確認し、全体を上書きしない |
| 戻り先URL | Webアプリの「設定 → Googleログイン → 設定を開く → Googleに登録する戻り先URL」。読み取り専用欄からコピー |
| クライアント設定JSON | Google Auth Platformからダウンロードしたファイル。ブラウザーの保存先を確認して、アプリのファイル選択欄から開く。Git・共有フォルダー・チャットには置かない |

### 2. Googleへの初回登録が未完了の場合だけ

1. [Google Auth Platform](https://console.cloud.google.com/auth/clients)を開き、SL Tour Finder用の管理可能なGoogle Cloudプロジェクトを選びます。プロジェクトの名前・IDを確認し、他アプリの設定を変更しません。該当登録がなければ、このアプリ用のCloud登録が必要です。
2. 初期案内が出た場合は現在の登録内容と所有者の連絡先を確認します。既存のプロジェクト名・アプリ名を変更する手順ではありません。通常のGoogleアカウントを含むスタッフが使える対象を選び、所有者1人専用にはしません。
3. 「クライアントを作成」で種類「ウェブアプリケーション」を選び、「承認済みのリダイレクトURI」に、アプリからコピーした戻り先URLをそのまま登録します。末尾の ?tourLogin=google まで一致が必要です。この方式では承認済みJavaScript生成元を使いません。
4. 作成したクライアントの設定JSONをダウンロードします。秘密情報を含むため、Gitリポジトリ・共有フォルダー・チャットへ置きません。[Google公式の登録手順](https://developers.google.com/identity/protocols/oauth2/web-server#creatingcred)

Apps Scriptの既定Cloudプロジェクトは通常、Cloud Consoleから直接管理できません。ただし本実装は登録したウェブクライアントへ直接HTTPSで接続するため、**既存Apps ScriptのCloudプロジェクトのひも付けを切り替える必要はありません。** その番号を勝手に変更しません。[Apps ScriptのCloudプロジェクト説明](https://developers.google.com/apps-script/guides/cloud-platform-projects)

Googleの基本的な本人確認のみのリクエストには、テストユーザーの個別登録を不要とする例外があります。本実装の本人確認はopenid emailのみです。スタッフを個別にテストユーザーとして並べる運用にしません。Google側の画面や組織ポリシーは実設定で確認します。一般公開・課金設定を自動で変更する処理はありません。[Google公式の対象ユーザー説明](https://support.google.com/cloud/answer/15549945?hl=en)

### 3. 接続設定が未登録の場合だけJSONを読み込む

1. Googleログイン設定ポップアップで、ダウンロードしたクライアント設定JSONを選びます。種類・サイズ・戻り先URLを検査し、読み込んだクライアントIDを表示します。秘密情報は表示しません。
2. 「設定を保存」を押します。指定グループがTourDBの編集共有先であることと、所有者からそのグループの在籍情報を照会できることを確認してから、接続情報を保存します。別アプリの戻り先しか含まれないファイルや、Android等の設定ファイルは受け付けません。
3. 「グループを照会」で再確認できます。照会できない場合は、所有者がグループの共有・メンバー閲覧設定を確認します。アプリは共有先やグループの設定を変更しません。
4. 設定保存の成功と、実メンバーのログイン成功は別です。次の実動作確認まで行います。

接続情報は、このApps ScriptのスクリプトプロパティTOUR_GOOGLE_CLIENT_ID / TOUR_GOOGLE_CLIENT_SECRET / TOUR_GOOGLE_LOGIN_VERSIONへ保存します。秘密情報を画面・候補DB・名簿・検索JSON・ログへ返しません。接続設定を変更すると、それまでの本人確認セッションは無効になります。

### 4. 実メンバーで確認

- 指定グループに所属し、TourDBへ個別共有されていないスタッフがログインし、候補を読み込めること。
- テスト用候補を編集・保存し、保存結果と確認履歴の確認者が本人になること。既存の実施記録は変更しません。
- グループ外のアカウントはGoogleで本人確認できても、候補を取得・保存できないこと。
- グループから外れた後は次の操作で再照会すること。アプリの許可キャッシュはありません。Google側の共有更新の反映時間は別です。

## グループ照会エラーと不足承認を確認する

旧画面の ACCESS_CHECK_UNAVAILABLE は、TourDBのDrive共有情報取得とGoogle Groupsの照会失敗を一つにまとめていました。このコードだけでグループの閲覧権限不足とは断定できません。修正版は、Googleが返したAPI未有効・不足スコープ等の既知理由、HTTP状態、グループ取得と在籍照会の段階を区別します。例外原文・HTTP本文・トークンを表示しません。

1. 対象TourDBのApps Scriptで、今回のMain.gsとIndex.htmlを全文置換して保存します。既存マニフェスト全体は上書きしません。
2. エディター上部の関数選択でcheckTourGoogleLoginGroupを選び、「実行」を押します。所有者のGoogle承認が求められた場合は内容を確認して承認します。この関数は共有・在籍情報を読むだけで、DB・共有・グループ設定・接続情報を変更しません。
3. このエディター実行は保存済みの最新コードを使うので、原因確認だけなら再デプロイは不要です。失敗時は実行ログの [TOUR_ACCESS_…] が失敗段階です。成功したら、必要なコード更新を既存デプロイの新バージョンへ反映します。接続設定が既に登録済みの場合は、JSONを保存し直す必要はありません。未登録の場合だけ初回手順へ進みます。

| 詳細コード | 分かっていること・次の確認 |
| --- | --- |
| DRIVE_API_DISABLED | GoogleがAPI未有効を返した。TourDB側のApps Scriptで「サービス」の＋からDrive APIを追加。既定Cloudは追加時にAPIが有効になる。標準Cloudを使用している場合は、その紐付き先でもDrive APIの有効化を確認 |
| DRIVE_SCOPE_REQUIRED | GoogleがDriveの承認範囲不足を返した。既存oauthScopesにdrive.metadata.readonlyがあるか確認し、所有者として関数を実行して承認を確認 |
| DRIVE_HTTP_401 / DRIVE_HTTP_403 | Driveが共有情報の照会を受け付けていない。グループ照会には到達していない。所有者のGoogle承認と対象DBを確認。403だけで理由を断定しない |
| DRIVE_HTTP_429 | Driveの取得回数制限。時間を空けて同じ照会を再実行 |
| DRIVE_REQUEST_FAILED / DRIVE_RESPONSE_INVALID / DRIVE_PERMISSION_PAGES | HTTP応答なし・応答形式・ページ取得の問題。グループ非所属や閲覧権限不足とは判定しない |
| GROUP_LOOKUP_FAILED | 指定グループの取得段階で失敗。アドレス・Google承認・表示権限等を確認 |
| GROUP_MEMBERSHIP_FAILED | グループは取得できたが在籍照会で失敗。まずエディターで関数を実行してGoogle承認を確認。承認済みでも失敗する場合に、所有者によるメンバー一覧の閲覧権限を確認 |
| GROUP_RESPONSE_INVALID | 在籍照会の応答形式が想定外。非メンバーと判定しない |

OAuthクライアントを登録したCloudと、TourDBのApps Scriptに紐付くCloudは同じとは限りません。APIの確認対象はTourDB側です。この修正はCloudの紐付け・API設定・共有設定を自動変更しません。必要性の根拠は[Google公式のサービス追加とAPI有効化](https://developers.google.com/apps-script/guides/services/advanced#enable_advanced_services)と[Groupsの在籍照会](https://developers.google.com/apps-script/reference/groups/group#hasUser(String))です。

保存前の確認は、実行者の在籍をhasUserで一度照会します。true/falseのどちらも照会を完了できたことの確認であり、スタッフの利用許可ではありません。スタッフには操作ごとのgetRole等による所属・活動状態の検査を引き続き行います。子グループ一覧は必要なときだけ展開します。

2026-11-27までの実画面確認では、GroupsApp.getGroupByEmailの呼出し権限不足を確認しました。修正した関数はAPI例外を捕捉する前に不足groups承認を要求し、エディター実行で「承認が必要です」が出ることを確認しました。その後、所有者から承認とGoogle本人確認完了の報告があります。これと、最新コードの反映・7日間保持・スタッフ本人の読み書き確認は別です。

## Googleの本人確認と所有者のサービス承認

スタッフがGoogleへ許可するopenid emailは、誰が操作するかを確認するためのものです。一方、所有者がApps Scriptへ与えるspreadsheets・groups・drive.metadata.readonly等は、アプリがDBや共有情報を扱うための承認です。写真アップロードのdriveも所有者側の承認です。スタッフ全員へこれらの業務用スコープや設定JSONの登録を求めません。

マニフェストへの記載だけで所有者の承認済みとは判断しません。エディターでの不足承認の要求は[Google公式のScriptApp.requireScopes](https://developers.google.com/apps-script/reference/script/script-app#requireScopes(AuthMode,String))、Webアプリの実行者の違いは[Google公式のWeb Apps](https://developers.google.com/apps-script/guides/web)を参照してください。

## 判定と保護

スタッフには、固定TourDBの指定グループへの編集共有と、そのグループまたは子グループへの活動中の所属が必要です。MEMBER・MANAGER・OWNERを認め、BANNED・INVITED・PENDINGを認めません。個別編集共有や、別グループへの所属だけではスタッフの利用許可にしません。担当者プルダウン用の名簿キャッシュ・任意登録したメールも認可の根拠にしません。

Googleが直接HTTPSで返した本人確認結果だけを受け付け、宛先・発行元・期限・確認用nonce・検証済みアドレスを照合します。画面から自己申告されたメール・IDトークンや、所有者のメールでアクセス者を代用しません。Googleの確認のstateは開始したGoogleセッションとブラウザー側の一時証明へ結び付け、PKCEも使用します。アプリ用のランダムなセッションはURL・検索JSONへ入れません。保持ONはこのアプリ専用キーのlocalStorage、OFFはsessionStorageに保存し、ログアウト時は両方から削除します。サーバー側はトークンそのものではなくハッシュをキーとして本人・期限・ブラウザー・接続設定版をScript Propertiesへ保存します。保管情報でグループ所属の再照会を省きません。CacheServiceの上限6時間と期限前の破棄に依存しない方式です。[Cacheの有効期限](https://developers.google.com/apps-script/reference/cache/cache)・[ブラウザー保存の寿命](https://developer.mozilla.org/en-US/docs/Web/API/Web_Storage_API)。期限切れ・旧設定版のセッション記録は次のログイン発行時に削除します。以前の最大6時間のセッションも元の期限内だけ受け付けます。[Google公式の本人確認方式](https://developers.google.com/identity/openid-connect/openid-connect)

読み込み中に同じ認可を繰り返さないよう、1つのサーバー処理の内部でだけ結果を共有します。外部照会後の保存直前には再照会し、書き込みロック中にGoogle本人確認のHTTPを行いません。ログアウト前の古い応答を、新しいログイン状態へ混ぜません。

| 表示・状況 | 意味と操作 |
| --- | --- |
| 管理者による初回設定が必要 | Googleログインの接続情報が未登録。所有者が上の手順を行う |
| 許可グループの所属を確認できなかった | 本人確認したアカウントを許可できなかった。所属しているアカウントで確認する |
| グループ所属の照会を完了できなかった | 取得失敗・閲覧権限・上限等。非メンバーとは断定せず、所有者が照会設定を確認する |
| 本人確認の期限切れ | 入力を保持した再確認画面を使う。保存は自動で繰り返さない |
| Googleの確認が完了しなかった | 元の画面の理由を確認して、Googleで再確認する |

今回の更新はMain.gs・Index.htmlを同じ版で置き換えて保存し、既存のデプロイを新バージョンへ更新して反映します。既存のGoogleログイン設定JSONの再登録、追加スコープ、DB初期化・列追加は不要です。Google側の最新変更のタブ終了・開き直し動作は未確認です。


## ソース公開前の確認

ソースリポジトリのセキュリティレビュー資料に、外部からの偽装拒否と、実行用スクリプト編集権限・写真参照の未修正事項を分けて記録しています。ソースの閲覧権限と、実行用プロジェクトやDB履歴を書き換える権限は別の信頼境界です。
