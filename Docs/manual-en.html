Get started

SL Tour Finder helps JapanHiroba’s SupportStaffJapan find destinations for Kankou Tour, manage candidate locations, and keep tour records. It is intended mainly for scenery, photography, and walking.

  1. Open the web app URL supplied by your administrator. Use an account belonging to the designated group. If identity confirmation appears, choose Sign in with Google. See sign-in and initial setup. Searching public Linden information does not require a Second Life login.
  2. Open Linden search → Search settings. The first search defaults to SSJ tour conditions: not toured and not guide-listed, with * as the keyword. A blank keyword means the same thing. If a saved search exists, its conditions and retrieved results are restored.
  3. Adjust the condition set or individual conditions as needed. Optional maturity, area, and category restrictions start disabled. Choose Done.
  4. Choose Search Linden. Read the results and check the locations you want to register.
  5. Choose Review selected imports, review the actions, and save. In the completion popup, check the DB save outcome separately from the automatic checks.
  6. After a tour, use Record visit to save the date, staff member, tour name, notes, and photographs.
A tour is intended to last about an hour, but area alone does not establish suitability. Assess sights, walking routes, and photo spots, and record your reasoning in the candidate’s notes.

All search conditions belong to one Search settings popup. Candidate editing, import review, and tour recording also use popups naming their targets. Check the result count, selected count, and operation status before proceeding.

Linden search displays all eligible candidates from the currently retrieved result page, subject to your conditions and result-group selection. It has no local page-size selector or display paging. The other four data screens retain Cards/List, 6/12/24/48 items per page, and page navigation.

Use Language / 言語 in the header for Automatic, Japanese, or English. Automatic follows the browser’s highest-priority language. If Google’s frame policy prevents full screen, the app expands within the available area. Small or short windows use scrolling to keep content and operations reachable.

Search settings and candidate selections are retained when navigating within the open page, but are not thereby saved. Confirm unsaved edits, such as candidate changes, before closing their forms. Reloading or closing the browser can discard unsaved input and selected files. Confirm the save outcome before leaving.

Selection controls, links and action buttons remain independent. Notes (annotations, verification evidence, etc.) appear in cards and lists, with the full text available in details. Matching web results show registered notes without copying them into the public search JSON.

Search settings and conditions

Done, Close, and Escape retain the settings and return to the main screen. Enter in the keyword field does not fetch results. Apply settings using Search Linden or the DB’s Search button. A notice identifies changes not yet applied to the displayed results.

TabConditions
BasicsCondition set, keyword, maturity, Destination Guide listing, and SSJ tour history.
AreaOptional minimum/maximum in m² and scope: target parcel, target parcels combined, or whole region.
CategoriesMultiple preset/custom checkboxes. Add custom names individually, not as a comma-separated list.
Additional conditionsDB-only on-site existence, connection to the same owner’s other parcels, decision, and check freshness.
RetrievalPages: 0–1000, default 0 = unlimited. Source-page interval: 0–60 seconds, default 0.
Save / resumeSave or load Linden search settings, retrieved candidates, selections, and display state as JSON.
  • Do not apply (show all) adds no restriction for that field and includes unknown values.
  • Maturity uses multiple checkboxes for General, Moderate, and Adult. Selected maturity values use OR; different conditions use AND. Explicitly selecting all three does not include unknown maturity.
  • Categories also use OR within the selection and AND with other conditions. An unrestricted category filter includes custom and uncategorized locations. New web results are not automatically assigned categories.
  • There is no fixed minimum area. An enabled range uses the retrieved area and its scope. An unknown area is not assumed to meet your numerical limits.
  • Existence and parcel connection are optional conditions. “Not connected” means an on-site check found no continuous connection to another parcel owned by the same owner.

Anonymous maturity access is limited. Adult alone is unavailable; mixed selections retain the results that can be retrieved and identify Adult as unavailable. The app does not request an SL login or bypass these restrictions.

Save and resume a search

This saves Linden search settings and state, not a backup of the DB or all application settings.

  • Included: keyword and conditions; retrieved candidates; source page and retrieval time; retrieval mode, page count, interval, cursor, and public check results; selections and import actions; Cards/List, result-group selection, and scroll position.
  • Excluded: the DB itself, unsaved candidate-edit notes, tour/check histories, staff directories, photo files, and photo-folder settings. The file includes user/DB identifiers to validate its target.
  1. Open Search settings → Save / resume.
  2. Choose Save Linden search to JSON to download SL-Tour-Finder-Linden-search.json. Your browser determines the download location.
  3. To resume, open the app for the same Google user and DB, then select that file using Load Linden search JSON.

Closing the browser stops retrieval. Loading only restores the search view; use Fetch more candidates to continue. It does not register candidates, run automatic checks, or search Linden again. A foreign-user/DB or invalid file is rejected without replacing the current state.

Where browser storage is available, the previous search also restores automatically. Storage failures, including large results exceeding browser capacity, are reported. Use JSON saving when needed (maximum input file size: 64 MiB). JSON is a snapshot at the time you save it, so save again before closing. Restoring does not refresh the original retrieval time. Use Search Linden when you want updated results.

Matches, pending checks, and result counts

Matches
The retrieved information and DB records allow the app to classify the location as meeting your conditions. An unused-for-SSJ condition may include provisional records described below.
Awaiting verification
Some required facts are unknown, so the app cannot establish whether the location meets the conditions. This is neither a verified match nor a verified mismatch.
Excluded
The location is classified as not meeting the selected conditions.

Matches and awaiting verification displays both groups. For example, an unknown guide status is pending when you require a confirmed unlisted location. “0 matches · 20 awaiting verification” does not mean all 20 failed your conditions.

Enter a page count (0–1000; default 0 = unlimited) under Search settings → Retrieval. Search Linden starts at page 1, then sequentially retrieves pages and checks each candidate in the guide. Results accumulate with duplicates removed, and all matching or pending candidates remain available by scrolling. Fetch more candidates continues from the saved cursor and remains available after completion. Result information shows conditions, provider total, accumulated count, time, and source.

Stop retrieval stops after an in-flight request finishes, or before sending during a wait. Only a normal empty source page or final page reports There are no more candidates. Exhaustion with no matches also reports that no candidates meet the conditions. Page-count completion, manual stops, and failures are distinct. Zero matches do not stop retrieval while source pages remain.

The observed source returned 20 items per page; that is not a guarantee of a permanent Linden page size. Identical results are reused for up to five minutes. New lookups run one at a time using the configured minimum interval (two seconds by default). Parse or connection failures wait the configured time after failure and retry up to the configured count (defaults: two seconds and three retries, four attempts including the initial request). There is no prefetch or crawling. Authentication, verification pages, and HTTP errors get no automatic retry.

Pale colorMeaning
GreenA new destination.
YellowA destination with recorded changes. Inspect the change history.
RedA destination confirmed gone, deleted, or requiring restoration. Restore it before using it as a new tour destination.

Condition classification and JSON generation use a Web Worker from DiscoveryWorker.html; cards and rows render in chunks. Linden communication runs in Apps Script. Check the actual processing mode under Search settings → Retrieval. When a Worker cannot start, the app uses cooperative chunks and does not claim a separate thread. Closing the browser stops retrieval. Automatic saving is asynchronous; confirm that JSON saving has finished before closing.

There are two intervals. The screen’s 0–60 seconds controls the wait between search pages. Setting it to zero does not remove server-side Linden request spacing or a source-requested wait. Server settings are TOUR_LINDEN_REQUEST_INTERVAL_SECONDS (1–10 seconds, default 2) and TOUR_LINDEN_MAX_RETRIES (0–5 retries, default 3).

Select and import candidates

  1. Check or uncheck individual candidates. Select this page selects the displayed candidates from the current retrieval.
  2. Selection options can select or clear all results you have deliberately retrieved. It does not fetch unseen pages. The selected count survives source-page and screen changes.
  3. Open Review selected imports. Check names, counts, and actions; expand the retrieved-information/change details if needed.
  4. Choose whether to save listing-photo URLs, then confirm with Import selected places. Retrieved names, SLURLs, owners, and areas do not need to be retyped. Each import accepts up to 500 candidates.
Existing-candidate actionOutcome
Update listing informationUpdates listing fields such as name, owner, area, maturity, and SLURL. Preserves decisions, notes, categories, and checks; blank or unknown incoming values do not erase known information.
Replace candidate dataReplaces listing data and resets fields such as the decision, notes, categories, and checks. Preserves visited facts, the candidate ID, and history. Review the differences carefully.
Do not importLeaves that candidate unchanged.

New locations offer Add new candidate or Do not import. An owner change invalidates the previous parcel-connection check. Import does not silently restore deleted candidates.

The completion popup separates the DB save from guide, region, and SSJ-history checks. An unavailable check does not necessarily mean the save failed. Pausing requests may leave remaining checks unprocessed. Reopen Import results (count) to inspect the results without fetching or saving again.

Candidates, decisions, deletion, and restoration

Registered candidates filters locations already stored in the DB; it is separate from discovering new Linden results. Edit / decision groups fields into Basics, Categories, Retrieved information, and Checks/corrections. Decisions are Candidate, Accepted, On hold, and Rejected.

After selecting candidates, use Actions for selected candidates for bulk editing, automatic checks, or deletion. Enable only the fields you intend to change, then verify the targets and count before saving. If a conflict is reported, reload and inspect the saved state.

More actions → Delete removes a candidate from the normal list while preserving visit and check histories. Restore the same candidate from Deleted. Histories use stable candidate IDs, so renaming or sorting sheet rows does not reassign them.

Do not bypass a confirmed-gone lock by merely editing an existence field or registering the same location again. Use restoration with an on-site check date and evidence. A candidate with tour records cannot be marked never visited.

Automatic checks and unknown information

Each place returned by Linden search is searched by name in the Destination Guide. A returned entry means Listed; a normally completed zero-result search means Not listed. For names with a parenthesized description, a zero result also triggers a search using the base name. An existing valid guide page keeps a place Listed even when its title is absent from the search index. Queries, dates, URLs, and counts are recorded as evidence. Open “Guide decision evidence” on a candidate to inspect the query and returned entry name. This is a name-search decision, not proof from a complete guide catalog.

Failures and unfinished checks remain pending rather than becoming Not listed. New acceptance requires a not-listed result and check date. Selections that no longer match are stopped before import, with their names shown.

Confirmed guide results use Listed / Not listed; SSJ tours use Conducted / Not conducted, without Y/N. Pending items show retrieval or retry status and offer Fetch guide information for this place or Fetch region information for this place. Unregistered web places can be checked without importing. Registered places use their candidate ID and version to save only the selected item. Successful pages are reused; only failed pages are retrieved again. Actual source-requested pauses remain enforced. Public check results are also retained with saved search state.

New registrations, imports, and Update information compare guide information, region information, and DB tour history, then record dates and evidence. App-mediated changes such as names and owners also record before/after values in Check history. This is not scheduled crawling or AI judgement.

Guide listing
A normal guide name-search result establishes Listed or Not listed. A missing URL or a 404 alone does not establish absence. Connection and parsing failures preserve prior facts and leave the check pending for retry.
Unused for SSJ tours
A location with zero records in this DB and no declared earlier tour is marked Not conducted, with the zero-record basis displayed separately. It is not proof that SSJ has never visited. Earlier records or staff confirmation can correct it.
Region registration
This concerns the region DB, not whether an attraction or parcel still exists on site. Not in DB is reserved for an explicit absence; connection failures and inconclusive responses are not absence.
On-site existence and connection
Record an on-site result, date, and evidence when needed. Finding the region does not verify that the facility still exists.

Check history records the candidate, field, time, result, and evidence. Keep unavailable and verified outcomes distinct; do not reinterpret unknown as unlisted or confirmed existing.

Tour records and photographs

  1. Use the candidate’s More actions → Record visit, or choose a destination from Visit history → Record visit.
  2. Enter the date, staff member, tour name, and notes. The initial staff ID is the accessing user’s personal email. Display names are linked separately. Other staff allows an arbitrary email/display name.
  3. Select several commemorative photos in the same form and add captions if needed.
  4. Choose Save tour record and photos. Without selected photos, only the tour record is saved. Inspect progress and completion results.
  • The limit is 10 photos per tour record, 5 MiB per image, JPEG/PNG/WebP. A configured Drive destination and the required authorization are necessary.
  • The tour record is saved first, then photos are uploaded sequentially under its ID. If only photos fail, retry the unsaved photos rather than recreating the tour record.
  • Use Visit history → Tour photos to view or add photos later. Different visits to the same candidate have separate photo records.
  • Removing a photo from a visit unlinks it; it does not delete the Drive original or audit history.
  • File selections survive navigation within the open app page, but a browser reload discards unsaved selections.

Linden listing photos reference their original image URLs; they are separate from uploaded tour photos. An unavailable source image may stop displaying. A photo does not prove on-site existence.

Staff, tour names, and storage

Settings → Staff profiles links email IDs and display names as separate fields. The choices include directly shared individuals and individual members that can be retrieved from shared Google groups. Group email addresses are not individual staff IDs.

If retrieval is partial, inspect the failed stage and reason; do not assume everyone was loaded. Refresh shared members or use Other staff as needed. Registering a staff profile does not grant access to the app.

Settings → Tour names manages the names available in tour-record dropdowns. Changing a staff or tour name does not rewrite historical snapshots. If you opened management from a record form, use Back to tour record to return to the draft.

The DB owner configures Settings → Photo storage with a Google Drive folder URL. The administrator must ensure the required folder access and Drive authorization. The app does not automatically change sharing permissions.

Google sign-in and group access

Staff access requires membership of ssj-sl-data-manager@googlegroups.com, the group with edit access to TourDB. There is no individual access registration. A staff-profile entry does not grant permission. The DB owner retains administrative access.

  1. Choose whether to Remember verification in this browser for 7 days on the sign-in screen. It is on by default, and your choice is saved for next time.
  2. Choose Sign in with Google and select the account belonging to the permitted group. If the Google tab does not open, use Open Google verification.
  3. After verification, the app tries to close the verification tab and continue in the original app. If it stays open, choose Close and return. If the browser still prevents closing, close the verification tab manually and select the original tab. Use Open the app if you closed the original tab.

Keep the original app tab open during Google verification. Wait until the candidate screen appears there before relying on remembered verification when reopening. This setting does not automatically save unfinished edits when you close the app.

Sign-out, expiry, changes to the sign-in connection, or cleared browser storage require verification again. If browser storage is blocked, the app explains that verification remains only in the current tab. Private browsing storage may be cleared when the private window closes.

The identity request uses only openid email. Group permission is checked on each operation even during the remembered period. Reverification retains the current draft and selection and does not automatically repeat a failed save.

Update an existing app with Google sign-in already configured
  1. In the Apps Script bound to the correct TourDB, replace Main.gs and HTML Index with the matching current versions and save. Keep the existing HTML DiscoveryWorker. Only if it is missing, add the full contents of src/DiscoveryWorker.html.
  2. Update the existing deployment to a new version. Keep execution as the owner and access for users with Google accounts. Use the normal /exec URL.
  3. Do not import the client JSON again when Google sign-in is already configured. Keep existing names, Cloud links, sharing, and photo authorization scopes. Do not initialize the DB or add columns for this update.
  4. Check data loading, remember on/off, and sign-out as an actual group member. If an authorized test candidate is saved, check both the saved result and the recorded actor. Successful Google identity confirmation alone does not prove that all staff operations work.
Only if initial Google sign-in registration is incomplete
  1. As the owner, open Settings → Google sign-in → Open settings and copy the Google callback URL for the existing app.
  2. In Google Auth Platform, confirm the intended existing project and register the callback for this app’s Web application client. Include ?tourLogin=google exactly. Do not change another app, or rename existing projects and apps.
  3. Select the client configuration JSON downloaded from Google in the same app settings panel and save it. The file contains a secret: keep it out of Git, shared folders, and chat. Do not create a per-person staff allowlist.
  4. Choose Check group access. If consent may be missing, the owner runs checkTourGoogleLoginGroup from the Apps Script editor’s function selector. If authorization is requested, the owner reviews and grants it, then runs the check again. A scope listed in the manifest is not proof that consent has been granted.
  5. Verify access as an actual group member and rejection as a nonmember. The app does not change group or sharing settings. Detailed administrator instructions are in docs/access.md.

Troubleshooting

A parse failure means the tool could not read the received page; it does not establish access denial. Parse failures do not pause all lookups, and the region check still runs independently. Identical failures are reused for up to 30 seconds. The UI distinguishes HTTP status, retry count, unsent requests, app-defined waits, source-requested waits, and the next allowed retry time. Old pauses with no evidence are labeled unknown. App-defined minimum waits are 60 seconds after HTTP 429, 300 seconds after 401/403, and 30 seconds after 5xx or a connection failure that persists after the retry. A longer source Retry-After takes precedence. These are application settings, not published fixed Linden limits.

SymptomWhat to check
Zero matches, with pending candidatesThis is not a retrieval failure. Review unknown conditions and display matches plus pending candidates if appropriate.
Retrieval failed or pausedThis is not zero results or proof a location is gone. Read the reason and do not repeatedly submit during a pause. Earlier results and selections remain.
Saved, but reloading failedDo not repeat the save. Use Reset / reload in the header to inspect the stored state.
Another change was detectedThis is a conflict check. Reload the current DB state and review it before repeating the operation.
Photos are unavailableCheck the folder, access, format, file size, and remaining allowance. A pending/unavailable thumbnail does not necessarily mean the original was deleted.
Only some shared members loadedInspect the retrieval stage and Google response, then contact your administrator. Discovering a shared group does not establish that all its members were retrieved.
Access deniedCheck that you selected your group-member account. A failed group lookup is different from confirmed nonmembership. The owner can check the group in Google sign-in settings. Access to this public guide is separate.
The app differs from this guideCheck whether the deployed app has been updated. This guide describes the repository implementation dated below.
Verification finishes but does not return to the appChoose Close and return in the verification tab. If closing is blocked, manually select the original tab. Keep the original app open during verification.
Verification is requested every time the app is reopenedCheck the remember setting, browser profile, expiry, sign-out, and cleared storage. Read any browser-storage limitation message.
Group lookup failsThis is not confirmed nonmembership. The owner runs checkTourGoogleLoginGroup in the editor and checks missing consent and the reported detail code.
For operators and administrators

In Apps Script, open Project Settings → Script Properties. Set TOUR_LINDEN_REQUEST_INTERVAL_SECONDS (integer seconds 1–10, default 2) and TOUR_LINDEN_MAX_RETRIES (integer 0–5, default 3). Three retries exclude the initial request, so at most four attempts are made. Zero disables retries. Invalid values prevent retrieval and display a configuration error. Changes apply to the next actual retrieval; valid cached results are reused. New requests share the same minimum interval. Source-requested waits and explicit denial still take precedence.

Preserve the intended DB, existing sheets, and candidate-ID relationships when updating. A routine code update does not require rerunning DB initialization. The source now uses execution as the owner. Initial Google setup and live group-member verification remain necessary. Do not resolve a mismatch by overwriting the whole manifest or broadening sharing/public access. Photo storage and shared-directory reads depend on the required authorization and visibility.

This guide describes behavior and operation, not verified live deployment, Google persistence, or every display configuration. The preview does not write to Google and does not substitute for live Linden search or Drive uploads. AI integration and scheduled crawling are not implemented.
